# Audit of `scripts/verify.sh` (2026-11-27)

Independent audit of `scripts/verify.sh` against the Definition of done in
`.goal/hostable-mvp.md`, on branch `goal/mvp` at `5602c48`. I read the scripts,
fixtures and tests, ran the checks, and tried to make the checks pass on
broken input. The working tree was clean before and after (`git status --short`
printed nothing).

## Headline finding: `set -e` is off inside every check

`run()` calls each check as `if "$@" >"$log" 2>&1; then`. Bash ignores
`errexit` for everything executed inside an `if` condition, including the whole
body of a function called there, even with `set -euo pipefail` at the top. So in
any check with more than one command, **only the last command's exit status
counts**. Reproduced with bash 3.2.57 (`/bin/bash`, which `#!/usr/bin/env bash`
picks here):

```
set -euo pipefail
f() { false; echo "after false (errexit ignored)"; diff <(echo a) <(echo b); echo last; }
if f >/dev/null 2>&1; then echo "PASS f"; else echo "FAIL f"; fi
# -> PASS f
```

This makes three checks able to pass while the DoD is not met (client, test and
e2e, desktop). Details are under each item below.

**Fix:** have each check function start with `set -e` (it does not carry into
the `if`-called function, so use explicit `|| return 1` after every command), or
run checks in a subshell that is not in an `if` context, e.g.
`( set -e; "$@" ) >"$log" 2>&1; rc=$?` and test `rc` afterwards. For the
`cargo test | tee` pipelines, also check `${PIPESTATUS[0]}`.

### 3. test: CONCERN (can pass while a test fails)
`cargo test --workspace 2>&1 | tee ...`: the pipeline's status is thrown away
(errexit is off, see above). The check then relies on (a) 9 named tests printing
`<name> ... ok` and (b) no `test result: FAILED` line. A test binary that dies
abnormally (abort, SIGSEGV, stack overflow in a non-main thread, `process::exit`)
prints **no** `test result: FAILED` line, and cargo stops there. If that binary
runs after the 9 named tests have printed `ok`, the check passes. Demonstrated
with a throwaway crate in the scratchpad:

```
#[test] fn a_memory_bomb_hits_the_cap() {}
#[test] fn zz_crashes() { ...; std::process::abort(); }
cargo exit=101
test zz_crashes ... error: test failed, to rerun pass `--lib`
  process didn't exit successfully: ... (signal: 6, SIGABRT)
name grep: found
NO 'test result: FAILED' line -> check_test's final grep would pass
```

Any binary cargo would have run after the crash is also skipped silently. A
compile error is still caught, because nothing runs and the named tests are
missing. Smaller point: the name grep matches substrings, so
`xa_memory_bomb_hits_the_cap ... ok` would satisfy `a_memory_bomb_hits_the_cap`.
Actual run: `PASS test`, 241 passed, 0 failed, 10 ignored (the e2e suite). All 9
required names appear with `... ok`.

### 5. client: FAIL (passes while broken; demonstrated)
`check_client` runs `npm ci`, `typecheck`, `npm test`, `build`, `size`,
`cargo test ... export_bindings` and `diff -r`, then ends with
`echo "protocol types match ts-rs output"`. Because errexit is off, **the echo's
status is the check's status**. A failing typecheck, unit test, build, size limit
or protocol diff all still print `PASS client`. Demonstration: I appended
`// AUDIT TAMPER` to `client/src/protocol/ButtonStyle.ts`, then ran
`VERIFY_ONLY=client scripts/verify.sh`:

```

VERIFY: SUBSET OK (client)
exit=0
target/verify/client.log:147: diff -r /var/folders/.../ButtonStyle.ts .../client/src/protocol/ButtonStyle.ts
target/verify/client.log:149: > // AUDIT TAMPER
```

The file was restored afterwards. The sub-steps themselves work: typecheck
clean, `ℹ tests 67 / pass 67 / fail 0`, build OK, 18.06 KB gzipped join-route
JS (limit 150 KB). `export_bindings` ran 20 tests, so the generated directory is
not empty. `size.mjs` walks the module entry scripts and modulepreloads in
`dist/index.html` plus their static imports, and fails over the limit. Its scope
is correct. The only problem is that `verify.sh` ignores all of their exit codes.

### 6. packs: PASS (one minor concern)
`scripts/packs.sh` runs as a separate process with its own `set -euo pipefail`,
so errexit is in force there. Ran it: 6 good packs built, signed and checked
(buzzer, wizards-duel, tideholm, riposte, standard-deck, ts-tictactoe), and each
one is re-checked against its pin. Each bad fixture must exit exactly 1 **and**

The crashing and looping fixtures are validly signed, so they get past the
signature step and fail at the rules stage, as intended. Minor: the good-pack

1. **Sandbox imports and limits: CONFIRMED.**
   - Imports: `check_imports` (crates/sandbox/src/lib.rs:434) rejects any import
     that is not `env.log` with signature `(i32, i32) -> ()`. It runs at build
     time, before instantiation. The linker defines only `env.log`.
   - Fuel: `consume_fuel(true)`; `set_fuel(fuel_per_call)` before every call

     `a_memory_bomb_hits_the_cap`,
     `a_module_asking_for_too_much_memory_up_front_is_refused`,
     `modules_may_only_import_log`.
2. **Host drops inputs not on the phone's current screen: CONFIRMED.**
   - `Room::handle_input` (crates/host-core/src/lib.rs:421) computes
     `allowed = slot.last_ui.is_some_and(|(ui,_)| ui.accepts(&input))`. When it
     is false, it only refreshes phones and never calls `on_action`.
   - `Widget::accepts` (crates/protocol/src/widget.rs:421) requires the id to be
     among the *enabled* inputs (`collect_inputs` skips disabled buttons and
     choices or hands with no enabled option) and checks the value's shape:
     null for buttons, real enabled options within min..max with no duplicates,
     text length, direction, touch and stroke bounds.
   - Test `input_for_a_widget_not_on_screen_is_dropped` passes.
3. **Each phone receives only its own `phone_view`: CONFIRMED.**
   `refresh_phones` (lib.rs:775) iterates players. For each it computes

   privacy test checks this end to end.
4. **Web Push matches RFC 8291: CONFIRMED.** I fetched RFC 8291 Appendix A from

## Re-audit after fae933d

Scope: commit `fae933d` changed `scripts/verify.sh` and `scripts/packs.sh`.
`scripts/ip_check.sh` and all product code are unchanged. As the coordinator
asked, I did not run the full `verify.sh` end to end; I used `VERIFY_ONLY`
subsets and a harness. The working tree is clean apart from this report.

### Mechanism
`run()` now runs `( set -euo pipefail; "$@" ) >"$log" 2>&1` between
`set +e` and `set -e`, and checks `$?` afterwards. The subshell is no longer in
an `if` condition. All ten `run NAME check_*` calls (lines 173–182) are plain
top-level commands.

One caveat I hit while testing. Bash ignores `set -e` inside a subshell
whenever that subshell runs in an `if`, `||` or `&&` context, even if the
subshell sets `-e` itself. My first harness wrapped calls as
`( run ... ) | grep ... || true`, and then every probe passed. This is an
artifact of the harness, not a bug in `verify.sh`, which never calls `run` in
such a context. A separate `scripts/verify.sh || ...` from outside is a new
process and is unaffected. Even so, a future edit like `run x check_x || true`
would bring the original hole back. I suggest a comment next to `run()`.
